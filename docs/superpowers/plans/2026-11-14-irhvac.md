# IR HVAC (`irhvac`) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A Home Assistant Marketplace (HACS) custom integration that adds infrared-controlled A/C units to Home Assistant from the GUI, encodes every command with pyhvac and sends it through a user-chosen HA infrared emitter entity.

**Architecture:** One config entry per unit. `entry.runtime_data` is an `IrHvacUnit` that owns the pyhvac device, the desired state, the last-sent ("previous") state, persistence (HA `Store`) and sending; the climate, switch, select and button entities are thin views over it. A pure `mapping` module translates between pyhvac capabilities/states and HA climate concepts; a `transport` module is the only code that knows the `infrared` building block (the RF door).

**Tech Stack:** Python 3.13+, Home Assistant >= 2026.6 (`infrared` component), pyhvac 0.2.x, pytest + `pytest-homeassistant-custom-component`, black, GitHub Actions (hassfest, HACS action).

**Spec:** `docs/superpowers/specs/2026-11-14-irhvac-design.md` (read it first; this plan argues from it).

## Verified facts (scratch prototype, HA 2026.10.4, pyhvac 0.2.0)

- `infrared_protocols.commands.Command(modulation=..., repeat_count=0)`; abstract `get_raw_timings() -> list[int]` (signed µs). Since infrared-protocols 5 / HA 2026.6.
- `homeassistant.components.infrared.async_send_command(hass, entity_id, command, context=None)` raises `HomeAssistantError` when the component is not loaded or the emitter is missing.
- Test emitter: `async_setup_component(hass, "infrared", {})`, then `await hass.data[homeassistant.components.infrared.const.DATA_COMPONENT].async_add_entities([FakeEmitter()])` where `FakeEmitter(InfraredEmitterEntity)` overrides `async_send_command(self, command)`.

- HA passes `target_temperature_step` through unconverted; a °F user's `set_temperature 75` reaches the entity as 23.89 °C; after snapping to 24.0 the state shows 75 (°F precision is whole degrees).
- pyhvac: `Device.encode(previous, target, actions=()) -> Command(signal, state)`; `command.state` is the normalised target (persist it). `Capabilities(modes, temperature, fan=None, swing_v=None, swing_h=None, features: Mapping[str, Choice], actions: Mapping[str, str])`. `Choice(values, labels)`; a value without a label displays as `str(value)`. `TemperatureRange(min, max, decimals)` with `.snap(celsius)`. `HvacState(power, mode, temperature, fan="auto", swing_v="off", swing_h="off", features={})`.

## Review Focus

1. A stored brand/model that pyhvac does not resolve. pyhvac never drops a model and keeps every released name resolving (enforced by a pyhvac test, Task 9), so this only happens through a bug or a hand-edited entry; setup must then fail with `ConfigEntryError` naming brand and model, not a traceback (Task 3).
2. A stored state that the model no longer accepts (e.g. a fan value removed): loading must not crash; the stored state is normalised through `device.normalise` and invalid previous is dropped to `None` (Task 3).
3. An emitter deleted or unavailable at send time: the service call raises `HomeAssistantError`, previous is unchanged, and the next successful send still uses the old previous (Task 3).
4. A temperature/humidity sensor reporting `unknown`, `unavailable` or a non-number: current value becomes `None`, no exception, no log spam beyond debug (Task 5).
5. A power sensor going `unavailable`/`unknown`: ignored, the unit's power is unchanged (Task 5).

```python
class IrHvacUnit:
    def __init__(self, hass, entry_id: str, brand: str, model: str, emitter: str) -> None
    device: pyhvac Device; capabilities: Capabilities; emitter: str
    state: HvacState            # desired state shown in HA; power = believed power
    previous: HvacState | None  # last sent; its power follows the power sensor
    async def async_load(self) -> None
    async def async_set(self, *, context=None, **changes) -> None
    async def async_action(self, name: str, *, context=None) -> None
    def power_reported(self, on: bool) -> None
    def add_listener(self, cb: Callable[[], None]) -> Callable[[], None]
```

Behaviour (decided here, from the spec):
- `__init__` raises `ConfigEntryError(f"pyhvac has no model {model!r} for {brand!r}")` when `registry.get_device` raises `KeyError`. Default state: `HvacState(False, caps.modes[0], snap(24.0))` normalised.
- `async_load` reads `Store(hass, STORAGE_VERSION, f"irhvac.{entry_id}")` holding `{"state": dict, "previous": dict | None}`; each is passed through `device.normalise`; one that fails (`ValueError`/`KeyError`/`TypeError`) is replaced (state → default, previous → `None`).
- `async_set(**changes)`: keys are `HvacState` field names; `features` merges into the current features. New desired = `device.normalise(replace(state, ...))`. If the new desired has `power False` and the current has `power False`, store it, notify, and send nothing. Otherwise encode `device.encode(previous, desired)`, send, and only after a successful send set `previous = state = command.state`, save (`store.async_delay_save(..., 1)`), notify. A send error propagates as `HomeAssistantError` and leaves `state` and `previous` unchanged.
- Sends are serialised with an `asyncio.Lock`; calls that arrive while a send is in flight coalesce: only the newest desired state is sent after the current send (intermediate states are dropped). *(Our call, replacing the spec's "about 0.5 s" timer: HA's frontend already sends the setpoint on slider release, and a timer would make service calls return before the send so errors could not reach the user.)*
- `async_action(name)`: `device.encode(previous, state, actions=(name,))`, send, then same bookkeeping. Sent whether on or off.
- `power_reported(on)`: no send; `state = replace(state, power=on)`; if previous is not None, `previous = replace(previous, power=on)`; save; notify. No-op when already equal.
